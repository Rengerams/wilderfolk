# Wilderfolk v0.6.3 Roadmap — Stories, Stewardship, and Simulation Truth

**Status:** Local planning and reconciliation draft — not approved for release.

**Target label:** v0.6.3.

**Purpose:** Deliver memorable, bounded colony stories and stewardship choices while closing the worker-authority, festival/venue, and security clarity defects that would otherwise make those additions unreliable or misleading.

## 1. Outcome

Version v0.6.3 should make Wilderfolk feel as though the existing colony simulation has consequences worth remembering. A player should be able to follow a small guided narrative thread, encounter one authored story rooted in ecology, visitors, rivalry, apprenticeship, or social history, and understand the practical responsibility of taming an animal.

The version must not treat story content as a reason to weaken simulation truth. Venue schedules must reconcile through the worker correctly. Festival staffing and duration must follow one explicit player-facing rule. Barracks patrols, Prison custody, and their UI language must describe the behavior the game actually provides. Every new story remains a bounded wrapper around an existing owner, cadence, command path, and save contract.

Every selected objective must preserve the worker-authoritative `WorldState`, typed command boundaries, named transitions, existing tick layers, and save/load rules. No objective may introduce a general quest engine, a second event bus, a new simulation tick layer, a UI mutation path, or unseeded story scheduling.

| Release promise | What the player notices | What must remain true |
|---|---|---|
| **The valley remembers** | A guided campaign foundation and one or more authored stories connect real colony facts to readable choices. | Existing ecology, visitor, diplomacy, apprenticeship, social, Chronicle, and story owners retain their decisions. |
| **Taming has a responsibility** | A tamed animal is no longer a permanent follower after one payment; its care state and shortage outcome are readable. | Animal care has one owner, a bounded cadence, explicit food source, save/worker coverage, and no hidden food drain. |
| **Festival and venue choices are truthful** | Chosen service hours and festival effects remain visible, authoritative, and understandable. | Worker command results reconcile every persistent venue field; staffing and duration policy are explicit and tested. |
| **Security behavior is legible** | The player can distinguish standing militia, active patrol visibility, Prison arrest eligibility, and custody policy. | Soldier and PrisonGuard remain separate roles; no generic Guard role, unbounded realtime scan, or speculative prison system is added. |
| **The current build is safer to extend** | The player benefits from fewer silent state/UI contradictions and clearer visual assets. | Family references, save normalization, worker transport, and presentation changes stay inside existing authority boundaries. |

## 4. Stability and authority work

### F1 — worker venue-schedule reconciliation

`setVenueSchedule` is already typed and the worker owns its command result. The remaining repair is to make every authoritative schedule field travel back through `SimTickDelta` and its application path. The task is not a new scheduling feature and must not add optimistic UI ownership.

| Contract | Required proof |
|---|---|
| Field transport | Tavern and Hotel schedules occur in delta type, extraction, and application. |
| Command result | A successful worker command leaves worker state, host state, and schedule panel on the same schedule. |
| Rejection | Invalid command leaves prior schedule intact in worker and fallback paths. |
| Save parity | A saved changed schedule loads identically before and after worker preparation. |

### F2 — festival policy and duration repair

The current code and the revised festival document disagree about whether a festival extends an innkeeper’s work shift. The developer must choose one policy before implementation proceeds. If the Tavern remains staff-open all festival, the UI, building description, fatigue feedback, and tests must say so. If festivals only make the Tavern visitor-open, worker shifts must remain the selected venue schedule.

Performer revelry must never make an already longer active festival shorter. The extension policy needs a named cap, a monotonic transition, and tests covering every festival origin.

### F3 — load-boundary canonicalization

Festival and venue state must be normalized once at the load boundary, not merely read defensively in scattered consumers. Legacy absent fields must receive canonical defaults. Invalid festival records must clear or normalize safely. This objective owns no new gameplay rule; it makes existing persisted rules dependable.

## 5. Authored stories: one bounded story at a time

The five authored-story design documents are retained as specifications. They are **not** implementation evidence. The first selected story must be a complete vertical slice rather than a shared quest framework.

### S1 — The Deer Parliament

Use existing ecology/hunting facts at the daily ecology boundary. The story may explain deer pressure humorously, but it must not add political deer, a second animal owner, or a per-deer quest field. A player-visible ecological response must use an existing owner and have an explicit bounded expiry or follow-up.

### S2 — The Traveling Theatre Company

Use an existing performer visitor group and real Chronicle/event-log facts. The factual record must never be overwritten by the performance. Visitor departure, cancellation, unsupported venue, and resource failure must consume or close the story safely.

### S3 — The Wedding That Nearly Started a War

Use one rival and the existing diplomacy/command pattern. It must not create a marriage simulation, population transfer, new diplomacy graph, or separate raid owner. Every delayed stage needs an absolute expiry and an idempotent resolution path.

### S4 — The Apprentice’s Terrible Invention Fair

Read existing apprenticeship/workshop facts. A selected invention must have a bounded, explicit effect and cleanup path. It must not become a technology tree, generic item inventory, or second apprenticeship owner.

### S5 — The Rumour Ledger

Use a real eligible event-log source at a weekly boundary. The factual event remains unchanged while the temporary interpretation resolves through existing social/reputation/rival owners. It must avoid population scans, per-settler gossip counters, and permanent hidden misinformation.

### Shared authored-story contract

| Contract | Required behaviour |
|---|---|
| Per-save frequency | One offer maximum per story key per save, including refusal, expiry, or cancellation. |
| Randomisation | Deterministic seeded eligibility window; no universal fixed start day and no unseeded start scheduling. |
| Spacing | Shared authored-story cooldown; blocked windows defer rather than force an offer. |
| Authority | One existing domain owner mutates each outcome; UI sends only typed commands. |
| Persistence | Active/offered/resolved state survives save/load when a story spans days. |
| Failure handling | Invalid choice, repeat command, missing resource, visitor departure, rival removal, and expiry are safe and idempotent. |
| Acceptance | Same-seed reproduction, seed variation, gate failure, choice outcomes, expiry, save/load, worker parity when applicable, and domain invariants are covered. |

## 6. Stewardship and Guided Campaign

### A1 — post-taming animal care

Taming currently spends food only at the moment of taming. Afterwards, no hunger, grazing, feeding, upkeep, or shortage behavior exists. Animal care must be proposed as its own small simulation feature before coding starts.

| Design contract | Roadmap requirement |
|---|---|
| Player goal | Keep each tamed animal healthy through a visible, understandable care responsibility. |
| Owner and cadence | Extend the existing tamed-animal lifecycle at an existing bounded daily decision point; do not create a UI owner or tick layer. |
| Food rule | Each tameable species has an explicit diet/source rule. The initial resource path must be visible and must not silently drain settlement food. |
| State | Add only the condition/feeding fields required for fed, warning, recovery, owner loss, and shortage outcomes. |
| Feedback | Show owner, condition, next care requirement, and shortage status in the selected-animal and settlement interfaces. |
| Failure safety | Shortage has one explicit, recoverable, player-visible policy selected before implementation; no hidden death or disappearance. |
| Persistence | New fields receive save normalization, worker preparation, delta/reconciliation, fallback, and malformed-save coverage as applicable. |
| Numbers | Feeding cadence, quantities, thresholds, and failure timing require a developer-approved starting-value proposal and playtest adjustment rule. |

### C1 — Guided Campaign integration

The campaign foundation is complete: five ordered chapters, journal state, daily progression projection, typed start/choice commands, persistence, and presentation already exist. It must remain a read-only projection of real story completion. No campaign code may manufacture an authored-story outcome just to advance a chapter.

The first integration occurs only after the corresponding story is finished, passing its own save/worker/invariant tests, and writes the matching namespaced resolved flag from the story’s actual owner.

## 7. Security and presentation truth

### Q2 — Barracks and Prison clarity

The intended first slice is clarity and contract alignment, not a security overhaul. Soldier and PrisonGuard are already distinct roles and must remain so. Barracks Soldiers provide standing militia strength continuously and perform a bounded daytime patrol reveal. The player-facing Barracks text must state the actual +14 base bonus, not +12.

Prison admission currently needs a completed staffed Prison, while prisoners remain confined through their stored sentence after admission. This is an institutional-custody model unless the developer explicitly approves active guard coverage. If active coverage is desired later, it requires a separate security roster, full-day interval design, save impact, bounded fatigue policy, explicit unsecured outcome, and focused tests. It must not be copied blindly from Hotel hours.

### V1 — character and map presentation

The staged resident art and world-map assets remain presentation-only. Final acceptance requires normal-map-scale review, clean transparent edges, readable adult/child silhouettes, coherent family styling, and a live-manifest integration decision. No art asset may assert canonical geography or create identity/state independent of existing entities.

### V2 — footpath and Taming Post review

The footpath prototype and dedicated Taming Post sprite remain presentation changes. Review them on the real map at ordinary and close zoom. Refine only visible seams, missing connections, or unreadable silhouettes. Do not change movement speed, collision, pathfinding, animal behavior, build cost, or save state as part of that art review.

## 8. Technical preparation and verification

### T1 — measured renderer/game chunk boundary

The circular `game-render → game → game-render` production warning and oversized game chunk remain open carryover work. Earlier chunk experiments that created additional cycles were rolled back. The next step is an import trace and a measured boundary proposal, not another `manualChunks` shuffle.

| Contract | Required proof |
|---|---|
| Import direction | Renderer code has no runtime path back into the game hub through a renderer dependency. |
| Presentation boundary | Renderer reads a stable render snapshot/contract and never owns world mutation. |
| Build result | Production build removes the named circular warning without suppressing it. |
| Performance | Record bundle topology, worker-ready latency, first render, and normal frame behavior before/after. |
| Non-goals | No renderer rewrite, WebGL migration, worker replacement, event bus, or speculative chunk split. |

### Q3 — regression and live acceptance

The current working set has strong focused evidence, including a recorded 82-file/448-test full suite and one-year deterministic invariant run for family cleanup. Those results do not replace live browser acceptance for schedule command reconciliation, visual asset readability, story choices, patrol visibility, or animal-care feedback.

Each selected objective must have a focused test first, then TypeScript, lint, full regression, relevant invariant checks, save/load checks for changed state, worker/fallback parity, deterministic replay where a seeded system is involved, and a short real player-path review.

## 9. Suggested implementation order

This is the safest order, not an automatic commitment.

1. Repair **F1** venue schedule delta reconciliation and add worker/host/fallback tests. It is a release-blocking authority defect in an already implemented feature.
2. Decide and repair **F2** festival staffing/duration policy, then complete **F3** load normalization. Do not build new festival content on unclear venue semantics.
3. Correct the small **Q2** Barracks copy error and choose visibility-only versus strategic-response patrol. Do not add High Alert without a defined raid-owner consequence.
4. Select one of **S1–S5**, preferably **S1 The Deer Parliament** as the smallest ecology-based vertical slice, and implement it end to end before creating shared story machinery.
5. Connect the completed story to **C1** only through its real resolved flag, then choose the next story based on player value and reuse of proven boundaries.
6. Prepare and approve **A1** animal-care rules before writing feeding code. The rules must specify source, cadence, state transition, shortage policy, UI feedback, and test plan.
7. Complete **V1/V2** normal-zoom presentation reviews; keep fixes render-only.
8. Triage **T1** separately through measured import tracing. It must not block an otherwise stable story slice unless build evidence shows a release-critical regression.

## 10. Acceptance gate for any selected objective

No objective is complete just because a function exists or a design document was written. The developer may accept a smaller scope, but a selected objective needs all applicable evidence below before it is marked verified.

| Evidence area | Required proof |
|---|---|
| Ownership and cadence | A Simulation Change Record names one owner, one cadence, allowed writes, explicit non-goals, and rollback path. |
| Authority boundary | Worker-authoritative state changes only through `gameTick()`, typed `applyWorkerCommand()`, or a named transition from one of them. |
| Focused behavior | Happy path, invalid gate/command, repeat action, timing boundary, expiry, and player feedback are tested. |
| Save and worker parity | New state is normalized at load, included in save/load, worker preparation, rollback, delta, command-result reconciliation, and fallback as applicable. |
| Invariants | Workforce, family, pregnancy, Moon Howler, Prison/security, ecology, or other affected invariants remain clean. |
| Performance | Realtime work is bounded; new spatial queries use existing indexes; daily/weekly work is measured where it can grow. |
| Player readability | Costs, eligibility, current status, blocked states, exception rules, and outcomes are visible without diagnostics. |
| Live acceptance | A short seeded player-path review confirms that the on-screen behavior matches the stated contract. |

## 11. Deferred or explicitly excluded work

The following are outside v0.6.3 unless the developer explicitly promotes them: a general quest engine; a global event bus; a new simulation tick layer; a new diplomacy or social graph; talking-animal AI; a per-settler rumour system; procedural invention/item generation; permanent hidden social penalties; a prison workhouse; a court/crime hierarchy; unbounded guard patrol scans; automatic Prison staffing; a complete renderer/engine rewrite; WebGL migration; and a bulk attempt to erase all static-audit warnings.

## 12. Developer decision points

Before coding the next vertical slice, the developer should decide:

1. Whether festival Tavern opening is **visitor-only** or also an exceptional all-day innkeeper shift.
2. Whether patrol is **visibility-only** or provides a defined raid-preparation/High Alert advantage.
3. Whether Prison custody is institutional after admission or requires active shift coverage.
4. Which authored story is the first v0.6.3 vertical slice and what its visible consequence should be.
5. Which explicit food source and recoverable shortage outcome animal care should use.
6. Whether the staged resident art is acceptable at real map scale before it replaces more legacy sprite paths.

At any point, the developer may reduce v0.6.3 to a smaller coherent update. The smallest truth-preserving release slice is **F1 + F2 + F3 + one selected story**: repair worker schedule truth, resolve festival policy/load safety, and add one complete authored experience rather than five disconnected specifications.
