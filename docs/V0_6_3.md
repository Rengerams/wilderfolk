# Wilderfolk v0.6.3 Roadmap

**Status:** Local planning draft — not approved for release.  
**Target label:** v0.6.3.  
**Purpose:** Add five authored story experiences that make apprenticeship, ecology, social history, visitors, and rival diplomacy feel personal without creating a second quest engine or simulation authority.

## 1. Outcome

Version v0.6.3 should make the colony feel as though its existing simulation produces memorable stories. Apprentices should attempt strange inventions, deer pressure should become a humorous ecological conversation, real events should generate bounded rumours, travelling performers should reinterpret colony history, and rival diplomacy should acquire a personal wedding-related chain.

Every story remains an authored wrapper around existing state owners. The stories must use existing worker-authoritative `WorldState`, typed commands, named transitions, event-log and Chronicle patterns, and existing daily, weekly, seasonal, visitor, ecology, apprenticeship, and diplomacy cadence owners.

## 2. Shared story cadence contract

Each of the five stories may start **at most once per game/save**. The story is considered consumed when its offer is created, including when the player rejects, ignores, cancels, or allows the offer to expire. Completing or failing the chain also prevents a second start in that save.

The start timing must vary between games. Each story uses a deterministic seeded roll derived from the colony seed and story-specific context, such as the current year, season, eligible event, visitor group, apprentice, or rival. The roll selects an eligible start window rather than a universal fixed day. The same seed and equivalent simulation history must reproduce the same result, while different seeds may produce different start timing.

The evaluation owner may remain daily, weekly, seasonal, annual, or visitor-boundary based on the story’s existing domain. That cadence is only the evaluation boundary; it does not make the story recurring. Unseeded `Math.random()` must not be used for start scheduling.

A shared authored-story cooldown prevents quest clustering. A new story may not be offered while another major authored story is active or while the shared cooldown is running. If a seeded window is blocked or its domain eligibility is not met, evaluation is deferred to a later eligible boundary rather than forcing the event on a fixed date.

| Contract | Required behaviour |
|---|---|
| Per-save frequency | One offer maximum per story key per save. |
| Randomisation | Seeded, deterministic window; no universal start day. |
| Reproducibility | Same seed and equivalent history produce the same eligibility result. |
| Minimum age | Every story has an explicit colony-day gate. |
| Spacing | Shared cooldown after another authored-story start or resolution. |
| State | Namespaced one-time flag or bounded typed record; no large conversation history. |
| Authority | Existing domain owner performs mutations; story code requests named transitions. |
| Failure handling | Reject, timeout, missing resources, visitor departure, or invalid choice must be safe and idempotent. |
| Persistence | Offer/active/resolved state survives save/load when the story spans days. |

## 4. S1 — The Deer Parliament

### Player experience

During one randomized seasonal window, deer gather near the colony in an unusually organized group. Villagers jokingly interpret the gathering as a parliament negotiating hunting rights, while the underlying facts remain real deer population, hunting pressure, food conditions, and ecology state.

The player may reduce hunting, create a preserve, ignore the gathering, or offer a symbolic food treaty. After several days, ordinary ecology rules show the consequence through wildlife recovery, farm-edge pressure, or a harmless deer-road nuisance.

### Implementation scope

Use existing ecology and hunting metrics at the daily ecology boundary. Add one bounded `DeerParliamentState` or reuse an existing ecology-memory record. Do not add political deer, a new animal AI, a new per-deer field, a full-population scan, or a new tick layer. The story may focus the camera on existing deer as a render-only presentation effect.

The minimum start gate is colony day 45, meaningful deer population, bounded hunting or grazing pressure, no active major story/disaster, and a clear shared cooldown. A seeded seasonal/day window selects the opportunity. `deer_parliament_offered` consumes the story slot when offered.

### Acceptance gate

The story is accepted when the player understands why the deer gathered, sees the humorous interpretation, chooses an ecological response, observes a bounded consequence through existing systems, and cannot trigger a second parliament in the same save. Tests must cover different seeds, same-seed reproducibility, cooldown deferral, thresholds, seasonal boundaries, invalid choices, and the absence of a new deer owner.

**Design document:** `docs/STORY_DEER_PARLIAMENT.md`.

## 5. S2 — The Traveling Theatre Company

### Player experience

A travelling theatre group arrives through the existing visitor system with costumes and an incomplete understanding of colony history. The troupe offers up to three scripts grounded in actual Chronicle or event-log records: a heroic first winter, an absurd wolf mistake, or a risky Town Hall scandal.

The player chooses hospitality, venue support, an improvised performance, or cancellation. On opening night, the player can correct the public story, let the legend grow, or interrupt the performance. The factual Chronicle remains unchanged while the stage interpretation creates a temporary bounded reputation, visitor-interest, or social effect.

### Implementation scope

Extend the existing visitor/story pattern with one `TheatreStoryState` linked to the existing performer visitor group. Select scripts only from facts that actually exist. Use the visitor group’s identity and lifespan rather than creating a second performer population model. The minimum start gate is colony day 50, an appropriate venue or allowed outdoor performance, a recent Chronicle entry, no active major story/raid resolution, and a clear shared cooldown.

Persist `theatre_story_offered` when the script card is created. Departure, cancellation, refusal, or completion consumes the story slot. Use a seeded roll from colony seed, visitor group ID, and story key to vary the eligible arrival window between games.

### Acceptance gate

The story is accepted when one performer group can host one coherent performance, the player can identify the real event behind the script, support costs and consequences are visible, the factual Chronicle is never overwritten, and visitor departure is safe. Tests must cover historical script availability, seed variation, cooldown deferral, support packages, resource failures, departure before performance, save/load, and duplicate prevention.

**Design document:** `docs/STORY_TRAVELING_THEATRE_COMPANY.md`.

## 6. S3 — The Wedding That Nearly Started a War

### Player experience

A rival settlement sends an invitation to a politically important wedding. Gifts, delays, envoy choices, and attendance are interpreted through the rival’s temperament and current relationship. The player may send a practical gift, an impressive gift, decline politely, or send a suitable adult envoy.

After a delayed response, the player may host a feast, attend with a delegation, or stay home and fortify the settlement. Outcomes range from peaceful alliance through uneasy respect and diplomatic insult to a rare recoverable catastrophe. Every rival consequence is explained in the event log and Chronicle.

### Implementation scope

Use a bounded `WeddingDiplomacyState` or namespaced story flags through the existing `pendingStoryEvents` and `storyFlags` pattern. The minimum gate is colony day 40, one rival settlement, a completed residence, a staffed production building, no severe disaster or active raid resolution, and a clear shared cooldown. A seeded daily-boundary roll using colony seed, rival ID, and story key selects the start window.

Persist `wedding_diplomacy_offered` when the invitation is created. Decline, timeout, or completion consumes the one-time story slot. Apply effects only through existing rival relationship, treaty, reputation, resource, visitor, and event-log owners. Do not create a new diplomacy graph, marriage simulation, population transfer, or quest engine.

### Acceptance gate

The story is accepted when a player can complete the three-stage chain, every choice exposes its cost or consequence, the rival response reflects the chosen action, the event log explains the result, and no raid, treaty, workforce, or save invariant fails. Tests must cover all gifts, envoy handling, delayed responses, seed variation, cooldown deferral, invalid choices, rival temperament branches, save/load, worker parity where applicable, and all four outcomes.

**Design document:** `docs/STORY_WEDDING_THAT_STARTED_A_WAR.md`.

## 7. S4 — The Apprentice’s Terrible Invention Fair

### Player experience

During one selected annual fair opportunity, an eligible apprentice presents three authored inventions intended to solve village problems. The player can fund an experiment, reject the proposals, or pay for a safer redesign. Examples include a self-counting granary, polite gate, emergency bell, or overbuilt plough.

After several days the demonstration produces a useful success, useful failure, comic malfunction, or rare recoverable dangerous failure. The player may keep, improve, or dismantle the invention. Effects remain temporary or bounded, and the Chronicle names the apprentice and master.

### Implementation scope

Read existing apprenticeship and workshop state at an existing annual or daily boundary. Use one bounded `InventionFairState`, three authored invention definitions, a seeded selection, visible costs, an absolute resolve day, and the owning domain’s named transition for any resource, fatigue, alert, research, or production effect. Do not add a general crafting inventory, technology tree, procedural item generator, uncontrolled physics, or second apprenticeship owner.

The minimum gate is colony day 30, teaching progress, a suitable master or completed workshop/forge/research building, no major active story, and a clear shared cooldown. Persist `invention_fair_offered` when the fair is offered. Rejection and expiry consume the story slot. A seeded roll based on colony seed, year, and story key selects the non-fixed opportunity.

### Acceptance gate

The story is accepted when an identifiable apprentice presents a comprehensible invention, the player knowingly accepts a visible risk, the result is funny but bounded, temporary effects expire correctly, and the colony recovers without repair or hidden permanent penalties. Tests must cover apprentice eligibility, seed variation, cooldown deferral, missing workshop, insufficient resources, deterministic invention selection, all outcomes, dismantling, and subsystem invariants.

**Design document:** `docs/STORY_APPRENTICE_INVENTION_FAIR.md`.

## 8. S5 — The Rumour Ledger

### Player experience

During one selected colony week, a real event from the event log becomes a rumour. It may concern a family event, Town Hall action, ecology change, frontier victory or loss, or scandal. The player can correct the record, encourage the rumour, ignore it, or investigate when a suitable official exists.

The result becomes bounded social interpretation. A corrected rumour restores trust, an encouraged rumour can create temporary morale or diplomatic interest while increasing future correction difficulty, and an ignored rumour may fade or affect one existing relationship. The factual event-log record is never changed.

### Implementation scope

Use a bounded weekly evaluation function that queries recent eligible event-log records without a full-population scan. Add one `RumourRecord` or namespaced story record, authored text templates with deterministic parameters, an expiry day, and one active rumour at a time. The minimum gate is colony day 60, Town Hall and relationship/history evidence, no major active story, and a clear shared cooldown. Use a seeded roll from colony seed, eligible week key, source event, and story key.

Persist `rumour_ledger_offered` when the card is created. Corrected, encouraged, ignored, or expired consumes the one-time story slot. Use existing reputation, morale, relationship, rival stance, Chronicle, and event-log owners for effects. Do not add a natural-language generator, social graph, per-settler gossip counters, permanent misinformation, or second event log.

### Acceptance gate

The story is accepted when the rumour is grounded in a real event, the player can inspect or influence its interpretation, the consequence is visible but bounded, the original truth remains intact, and no card flood occurs. Tests must cover seed variation, same-seed reproduction, cooldown deferral, no-source behaviour, deterministic templates, all responses, expiry, subject cleanup, bounded relationship effects, and the absence of population scans.

**Design document:** `docs/STORY_RUMOUR_LEDGER.md`.

## 9. Recommended implementation order

The recommended order is **S1 The Deer Parliament**, **S2 The Traveling Theatre Company**, **S3 The Wedding That Nearly Started a War**, **S4 The Apprentice’s Terrible Invention Fair**, and **S5 The Rumour Ledger**.

The Deer Parliament is the smallest prototype because it uses existing ecology facts and one bounded response record. The Traveling Theatre Company should follow as the first full visitor/story chain. The Wedding then exercises the existing rival diplomacy and delayed-choice patterns. The Apprentice fair follows once the story card and timed experiment patterns are proven. The Rumour Ledger should be implemented after the event-log query and Chronicle inspection contract are stable because it touches the broadest interpretation surface.

## 10. Cross-feature non-goals

These five stories must not introduce a general quest engine, a global event bus, a second simulation tick, unseeded random scheduling, a new diplomacy graph, a new social graph, a general crafting inventory, talking animal entities, per-settler gossip counters, permanent hidden penalties, or direct UI mutation of authoritative state.

Every implementation must include a Simulation Change Record, a named owner, cadence declaration, save/load decision, explicit rejection and expiry path, worker parity coverage where commands cross the worker boundary, and a full regression check before release consideration.

## 11. Roadmap acceptance gate

The v0.6.3 story set is ready for release consideration only when all five stories have passed their individual acceptance criteria, each can start only once per save at a seeded non-fixed time, the shared cooldown prevents clustering, save/load preserves active delayed state, the event log and Chronicle explain outcomes, and the full type, test, lint, build, and diff checks pass.
